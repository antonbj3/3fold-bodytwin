# MECHANISM DIFF RECONCILE — the self-computed-vs-JointReaction gap, resolved (2026-07-21)

Executes the operator's task: pin down the exact divergent term between the self-computed
(`R − Σmuscle-crossing`) and `opensim.JointReaction` contact-force methods, which the knee, hip,
and ankle certs each found disagreeing by a remarkably consistent ~1.68-1.69× (`docs/
MECHANISM_JOINT_FORCE_VALIDATION.md`, `MECHANISM_HIP_FORCE.md`, `MECHANISM_ANKLE_FORCE.md`), diagnosed
there — but never numerically resolved — as a differentiation-scheme difference. Every number below
is machine-measured this session (`scripts/msk/reconcile_diff_scheme.py`, exit 0), not recalled.
Isolation respected: `.venv-msk` only; `validate_joint_force.py` / `static_opt_knee.py` /
`validate_hip_force.py` / `validate_ankle_force.py` imported and called, never edited; SO/JR output
and OpenSim's own source tree read in place; no git operations.

## Headline result

**The ~1.68-1.69× gap was NOT a differentiation-scheme difference. It was a sign bug** in
`static_opt_knee.py`'s `knee_crossing_muscles_and_forces` (an inside/outside path-index ternary
backwards in both branches), which silently negated the muscle-crossing force vector at all three
joints. A parallel/sibling investigation found this first (`docs/MECHANISM_SIGN_BUG_AUDIT.md`,
knee+hip only, toy-case + algebraic-identity method) and applied the fix at source
(`docs/MECHANISM_SIGN_BUG_REMEDIATION.md`) — at the time this session directly measured it (below),
the fix was present but uncommitted in the working tree; it is now committed (`a1886d303`, "msk:
SIGN-BUG REMEDIATION"). Fixing the sign collapses the gap to 0.001–0.07% at all three joints,
independently re-derived here via a completely different route and **extended to the ankle**, which
the audit's own stated scope explicitly excluded ("knee+hip only, per the task").

| joint | published self-computed (bug) | ratio vs anchor | **corrected self-computed** | official `JointReaction` | corrected vs JR |
|---|---:|---:|---:|---:|---:|
| knee | 233.20 %BW | 0.903 | **391.10 %BW** | 391.11 %BW | **0.0039%** apart |
| hip | 235.30 %BW | 0.859 | **386.77 %BW** | 387.04 %BW | **0.070%** apart |
| ankle | 286.68 %BW | 0.601 | **484.49 %BW** | 484.48 %BW | **0.0014%** apart |

The corrected numbers land almost exactly on `opensim.JointReaction`'s own peak **value and time**
at all three joints (knee/ankle: identical peak time; hip: the corrected peak time snaps from 0.67s
onto JointReaction's own 0.55s) — the strongest evidence the correction, not the original, is
physically right, since JointReaction is a structurally independent Simbody code path
(`calcReactionOnChildExpressedInGround`, fed by `Model.realizeAcceleration`) that never calls the
buggy function at all.

## 1. What was built, and why it turned out not to be the answer (reported, not hidden)

Per the task, a full matched-differentiation apparatus was built and validated **before** the sign
bug was found:

1. **Mechanism verified live from OpenSim's own C++ source** (a matching tree exists on this
   machine, `/media/anton/8838D60F38D5FBDE/mechanism_data/opensim_jam_build/opensim-core-jam/`, not
   assumed from memory): `lowpass_cutoff_frequency_for_coordinates=6` (grepped from the actual
   patched SO/JR setup XMLs) drives `AnalyzeTool.cpp`'s coordinate loader
   (`Storage.pad`+`Storage.lowpassIIR` — a bidirectional 3rd-order Butterworth, effectively 6th-order
   zero-phase — then `SimbodyEngine::formCompleteStorages` fits a **quintic `GCVSpline`** and takes
   its 1st derivative for speeds). Critically, **no acceleration is ever built from data at all**:
   `JointReaction::record()` (`Analyses/JointReaction.cpp:544-577`) overrides **every** actuator's
   force to the exact Static-Optimization value, then calls `Model.realizeAcceleration` — a genuine
   forward-dynamics solve, not a second differentiation.
2. **Synthetic-control validation** (before trusting this on real gait data, per this repo's own
   discipline): a 1 Hz in-band + 25 Hz out-of-band synthetic signal, run through the exact same
   `Storage.pad`/`Storage.lowpassIIR(6)`/`GCVSplineSet(5)` API calls, reproduced the analytic
   position/velocity/acceleration to 0.009%/0.27%/2.0% relative error — **PASS**, gating the rest of
   the script.
3. **A matched-acceleration experiment**: reconstruct the exact JointReaction-consistent Cartesian
   COM acceleration (6Hz-filtered spline Q,U → every actuator overridden from the SO `force.sto` →
   `Model.realizeAcceleration` → `Body.findStationAccelerationInGround`) and swap **only** this
   acceleration source into the self-computed method's own, otherwise-unmodified Newton's-law
   formula, to see whether the resulting contact force moved toward JointReaction's.

Running this apparatus's own **reproducibility gate** — Pass A must reproduce the already-published
self-computed numbers before anything built on it can be trusted — is what surfaced the real
finding: Pass A (which imports, unmodified, `static_opt_knee.knee_crossing_muscles_and_forces`)
reproduced **391.10/386.77/484.49 %BW, not 233.20/235.30/286.68 %BW**. Since `R_old` (the pure,
muscle-free reaction) matched the published number to 14 significant figures, and the muscle-force
magnitude also matched to 14 significant figures, the discrepancy could only be in the final
combination sign — `git diff HEAD -- scripts/msk/static_opt_knee.py` confirmed an uncommitted,
working-tree-only fix to the crossing-muscle direction convention, cross-referencing
`docs/MECHANISM_SIGN_BUG_AUDIT.md` (a parallel/sibling investigation already on disk, independently
reaching the same 391.10/386.77 %BW numbers via a completely different method: a toy-case
ground-truth unit test plus an algebraic identity `F_fixed = 2·R_old − F_buggy`).

## 3. Term-by-term diff at the peak frame (what the task asked for directly)

At the knee's peak frame (t=0.51s), decomposed by body (self-computed's own Newton's-law free-body
cut, `tibia_r, talus_r, calcn_r, toes_r`):

| quantity | value |
|---|---|
| `R_old_vec` (pure reaction, no muscle knowledge) | (−41.5, −751.7, 19.6) N &nbsp;→&nbsp; 98.2 %BW |
| `muscle_force_contrib_vec` (13 crossing muscles × SO tension × live path geometry) | (1436.3, 1853.4, 178.6) N &nbsp;→&nbsp; 306.6 %BW |
| **subtraction** `R_old − F_muscle` (current on-disk code) | (−1477.7, −2605.1, −159.1) N &nbsp;→&nbsp; **391.10 %BW** |
| **addition** `R_old + F_muscle` (bug-equivalent) | (1394.8, 1101.6, 198.2) N &nbsp;→&nbsp; **233.19 %BW** |

Both `R_old_vec` and `muscle_force_contrib_vec` are individually reproduced to 14 significant
figures against the already-published sub-components (`"muscle_crossing_force_peak_pct_bw":
306.63656710743663`) — the entire divergence is the sign of one combination step, not any upstream
kinematic or dynamic term. The y-component sign is the tell: bug-buggy reads **+1101.6 N** (looks
like a plausible push); corrected reads **−2605.1 N** (a compressive pull, 157.7° from the buggy
vector — the classic "near-total sign flip modulated by `R_old`" signature) — this is exactly why a
vector-**norm**-based consumer (this family of certs) could not see the bug the way a **signed**
axial-projection consumer (the spine cert, `docs/MECHANISM_SIGN_BUG_AUDIT.md` §3) immediately did.

## 4. Corrected knee/hip/ankle contact forces (the task's explicit deliverable)

| joint | corrected peak contact force | at t | vs official JointReaction | vs in-vivo/published anchor |
|---|---:|---:|---:|---:|
| knee | **391.10 %BW** | 0.51 s | 391.11 %BW (0.004% apart) | OrthoLoad median 258.22 %BW → ratio **1.515** (overshoot) |
| hip | **386.77 %BW** | 0.55 s | 387.04 %BW (0.070% apart) | OrthoLoad median 273.93 %BW → ratio **1.412** (overshoot) |
| ankle | **484.49 %BW** | 0.58 s | 484.48 %BW (0.001% apart) | published midpoint 476.7 %BW → ratio **1.016** (near-exact) |

All three now land at or moderately past their respective anchors — the "self-computed lands just
under, JointReaction moderately overshoots" framing in the original three certs does not survive;
both methods now agree with each other and both overshoot OrthoLoad (knee/hip) or land almost
exactly on the published band (ankle). This is a **materially different physical conclusion** from
the original certs, not merely a numeric correction — see honest gaps §7.4.

**This overshoot is not idiosyncratic — it is a documented tendency of exactly this class of
method**, per a citation surfaced by the sibling remediation and re-confirmed here: Moissenet, Chèze
& Dumas, *J Biomech* 2014, DOI [10.1016/j.jbiomech.2013.10.015](https://doi.org/10.1016/j.jbiomech.2013.10.015):
*"Musculo-tendon forces and joint reaction forces are typically estimated using a two-step method...
the joint reaction forces are usually overestimated."* This twin's method is exactly that two-step
pattern (R computed from kinematics+GRF alone, muscle tensions computed separately, combined
post-hoc) — the corrected 1.4-1.5× knee/hip overshoot is consistent with, not contradicted by, the
published literature on this method class.

## 5. The differentiation-scheme apparatus: built, validated, and left honestly OPEN as a residual question

The task asked to be symmetric — "the gap is real physics, not a bug" is as valid an outcome as
"fixed it." Having found a different, dominant cause (the sign bug, which fully explains the
originally-reported gap to <0.1%), the **narrower** residual question — is there a small,
genuinely-differentiation-scheme-driven discrepancy left over, beneath the sign bug — was pursued
with the built apparatus (Pass A/B, `reconcile_diff_scheme.py` STEP 3-7) but **not resolved**:

- Pass B's `Model.assemble()` gives **inconsistent** results for this model's dependent "rolling
  knee" coordinates (`knee_angle_{r,l}_beta`, confirmed live via `Coordinate.isDependent(state)
  == True`, slaved to `knee_angle_{r,l}` by a `CoordinateCouplerConstraint`-style mechanism) —
  explicitly **not** independently drivable from their own spline fit (doing so was an early,
  ultimately-refuted hypothesis for a >7800 m/s² `toes_r` acceleration blowup this script's own
  absurdity-ceiling gate caught).
- A fresh-model-per-frame probe (eliminating any sequential warm-start/history dependence) gave
  **yet a third** set of values at the same time points, refuting the warm-start-hysteresis
  hypothesis without producing a diagnosed replacement.
- The resulting Pass-B "matched" numbers (595-985 %BW range, peaking in a broad, non-edge-localized
  region growing across the second half of the trial) are **not** reported as a measurement of the
  residual differentiation effect — they are reported as an unresolved implementation issue in this
  script's own from-scratch dynamics reconstruction, explicitly flagged `status: OPEN` in the
  results JSON, not forced into a false "confirmed" or "refuted" either direction.
- This uncertainty does **not** propagate to §1-4 above: those rest on direct re-execution of the
  real, unmodified cert functions plus an exact algebraic identity, never on Pass B.
- The best available bound on the residual question comes from the sibling audit's own,
  independently more robust method (algebraic identity on the SAME already-validated SG-Cartesian
  acceleration, not a new dynamics reconstruction): "any genuinely remaining differentiation-scheme
  effect is now bounded at ≤0.07% — noise level, not the dominant term it was believed to be."

## 7. Honest caveats (full list)

1. **The differentiation-scheme apparatus (§5) did not reach a clean answer** on the narrow residual
   question — this is the primary open item. Time-boxed per LEAN discipline once the dominant cause
   (the sign bug) was found and triple-confirmed; resuming it would mean debugging Simbody's
   constraint-solver behavior for a `CoordinateCouplerConstraint`-slaved coordinate on a
   `PolynomialFunction`-coupled `CustomJoint` — a real, bounded, non-trivial follow-on, not a quick
   fix.
2. **This script does not fix `static_opt_knee.py`, `validate_hip_force.py`, or
   `validate_ankle_force.py`** (explicit isolation instruction: import/read, never edit) — the
   sign-bug fix was applied and (since this session's own measurements were taken) committed by
   others (`a1886d303`); this document does not add, remove, or alter it, only measures its
   consequences via direct, unmodified function calls.
3. **`docs/MECHANISM_JOINT_FORCE_VALIDATION.md`, `MECHANISM_STATIC_OPT.md`, `MECHANISM_HIP_FORCE.md`,
   `MECHANISM_ANKLE_FORCE.md` were not edited by this script** — but, checked live rather than
   assumed stale, all four already carry a `## ⚠ CORRECTION (2026-07-21)` banner (or, for the
   knee-reaction-only doc, a pointer) from the sibling `docs/MECHANISM_SIGN_BUG_REMEDIATION.md`,
   which also directly regenerated `hip_force_validation_results.json` and
   `ankle_force_validation_results.json` on disk with the corrected numbers (confirmed via file
   mtime, 15:59). `static_opt_knee_results.json` (the knee's own JSON) was deliberately left
   un-regenerated by that remediation (would require a fresh, expensive Ipopt re-run) and still
   holds 233.20 %BW on disk — this document's own §1-4 numbers do not depend on that file's current
   contents (see §0).
4. **The corrected ratios (1.515 knee, 1.412 hip, 1.016 ankle) change the physical conclusion**, not
   just the number: the original certs' "self-computed lands just under OrthoLoad, JointReaction
   moderately overshoots" framing no longer holds; both methods now overshoot (knee/hip) or land
   almost exactly on the anchor (ankle). Whether a ~41-52% OrthoLoad overshoot is itself concerning
   is a separate question this document does not adjudicate (same scope boundary the sibling audit
   drew for itself).
5. **Single trial, right side only** (subject2 `walking1`) — unchanged scope caveat inherited from
   every upstream cert in this family.
6. **The sign bug's root cause (why the ternary was backwards, and when/how the working-tree fix was
   introduced) was not investigated here** — out of scope; this document measures consequences, the
   sibling audit already did the forensic toy-case work.
7. **OrthoLoad/published anchors (258.22 / 273.93 / 476.7 %BW) reused verbatim**, not re-parsed or
   re-verified — out of scope, unchanged from every upstream cert.
8. **The Pass-B apparatus, despite being unresolved for its original narrow purpose, is validated,
   reusable infrastructure** (synthetic-control-passed 6Hz-filter + quintic-spline replication via
   real OpenSim API calls, and a source-verified replication of JointReaction's actual
   override-actuation + `realizeAcceleration` mechanism) — a genuine asset for future MSK work on
   this model family, not a wasted effort, even though it did not answer the question it was built
   for.
